# 진단 규칙과 최적화 연산자

에이전트 **한 벌의 실행 기록**을 읽고, 제작자가 밝힌 **목표에 맞춰** 구성을 진단한다.
같은 데이터라도 목표가 다르면 제안이 달라진다. 그것이 이 스킬의 핵심이다.

---

## 0. 목표 확인 — 진단 전에 반드시

사용자는 스킬을 부를 때 자연어로 목표를 말한다. 그것을 아래 넷 중 하나로 해석한다.

| 목표 | 뜻 | 사용자가 이렇게 말한다 |
|---|---|---|
| `COST` | 품질을 크게 해치지 않는 선에서 **비용을 줄인다** | "돈 아끼고 싶어", "저가 모델로 갈 수 있나", "토큰 줄여줘" |
| `QUALITY` | 비용이 늘더라도 **정확도·안정성을 높인다** | "성능이 우선", "틀리면 안 돼", "비싸도 좋으니 정확하게" |
| `LATENCY` | **응답 속도**를 줄인다 | "느려", "응답 빨라야 해", "실시간이야" |
| `BALANCED` | **명백한 낭비만** 잡는다 (기본값) | 목표를 안 밝혔을 때 |

**목표를 못 정하겠으면 물어봐라.** 추측해서 진행하지 마라.
정했으면 보고서 맨 앞에 **"이 목표로 진단했다"**를 반드시 명시한다.

### 이 스킬이 모르는 것 — 모델 가격

로그에는 **모델 이름과 토큰 수**가 남지만 **요금표는 없다.**
그러니 `gemini-3.6-flash`가 비싼지 싼지 이 스킬은 알 수 없다. **추측하지 마라.**

- 말할 수 있는 것 — "이 단계가 전체 토큰의 60%를 쓴다" (측정값)
- 말할 수 없는 것 — "이 모델은 비싸다" (요금표가 없다)

따라서 모델 교체를 제안할 때는 **현재 모델명을 밝히고 방향만 제시한다.**

> "`DECIDE`가 토큰의 60%를 쓰고 현재 `gemini-3.6-flash`를 사용합니다.
>  결과가 3회 반복 내내 동일하므로 더 낮은 등급 모델로 내려도 될 가능성이 높습니다.
>  다만 실제 절감액은 요금표를 알아야 계산되므로 여기서는 추정하지 않습니다."

사용자가 **쓸 수 있는 모델 목록이나 단가를 알려주면** 그때는 구체적으로 계산해라.
모르면 "어떤 모델을 쓸 수 있는지 알려주면 더 구체적으로 제안하겠다"고 물어라.

예외: `model_id`가 `local-deterministic` 처럼 **명백히 모델 호출이 아닌 경우**는
토큰이 0으로 측정되므로 비용 없음이 확실하다. 이건 단정해도 된다.

### 제약 조건도 함께 받는다

사용자가 지키고 싶은 선을 말할 수 있다. 있으면 모든 제안이 이것을 넘지 않아야 한다.

- "성공률은 95% 아래로 떨어지면 안 돼"
- "케이스당 토큰 3000 이하"
- "안전 위반은 절대 0이어야 해"

제약을 위협하는 제안은 **내지 말거나, 위험을 명시**하고 낸다.

## 1. 먼저 계산할 것 — 목표와 무관하게 항상

### 1-1. 단계별 비용 프로파일

`provider_calls`를 `node_role`로 묶는다.

| 지표 | 계산 |
|---|---|
| `calls` · `tokens` · `latency_ms` | 그 단계의 호출 수 · 토큰 합 · 지연 합 |
| `token_share` · `latency_share` | 전체 대비 비중 |
| `models` | 그 단계가 쓴 `model_id` 집합 |

### 1-2. 단계별 개입률

`traces`를 `node_role`로 묶는다.

- `runs` — 실행 횟수
- `intervention_rate` — `outcome == "fail"` 비율. **그 단계가 흐름을 바꾼 비율**
- `VERIFY_REASONING`의 `fail`은 오류가 아니라 "검증기가 문제를 잡아 되돌렸다"는 뜻이다

### 1-3. 반복 안정성

같은 `testcase_id`의 모든 반복에서 아래가 전부 같으면 그 케이스는 **결정론적**이다.

- `task_success` · `policy_correct` · `stop_reason` · `retry_count` · `tool_schema_valid`
- `agent_output`의 sha256 해시

`stability_rate` = 결정론적 케이스 ÷ 전체 케이스

### 1-4. 품질·효용 지표

**분모는 trial 수다. testcase 수가 아니다.** 그래야 값이 항상 0~1에 들어온다.

```
success_rate    = task_success 가 true 인 trial 수  ÷  집계에 쓴 trial 총수
policy_accuracy = policy_correct 가 true 인 trial 수 ÷  집계에 쓴 trial 총수
```

반복이 3회면 같은 케이스가 3번 세어지는 것이 맞다. 그것이 실제 실행 성공률이다.
케이스 단위로 묶지 마라 — "한 번이라도 성공"으로 세면 낙관적으로 부풀고,
"모두 성공"으로 세면 비관적으로 깎인다. 둘 다 실제 성공률이 아니다.
- `retry_runs` / `retry_recovery_rate` — 재시도가 실제로 살려내는가
- `failure_reasons` — 실패 기록의 `stop_reason` 분포

## 2. 공통 규칙 — 목표와 무관하게 항상 검사

| ID | 조건 | 심각도 | 유형 |
|---|---|---|---|
| **D-01** | `safety_violation == true`가 1건이라도 있음 | P0 | SAFETY |
| **D-02** | 어떤 단계의 `token_share`가 35% 이상 | 정보 | COST_HOTSPOT |
| **D-03** | 실패 기록의 `stop_reason`이 한 종류에 70% 이상 몰림, 또는 `failed_call_count > 0` 인 기록이 20% 이상 | P1 | FAILURE_PATTERN |
| **D-04** | `scaffold_config`에 켜져 있는데 `traces`에 한 번도 안 나타남 | P1 | DEAD_STRUCTURE |

D-02는 그 자체로 문제가 아니다. **어디를 먼저 볼지 알려주는 이정표**다.
D-04는 목표와 무관하게 잘못된 설정이다 — 켜 놓고 안 쓰는 것은 어느 목표에도 이롭지 않다.

## 3. 목표별 규칙

### 3-1. `COST` — 비용을 줄인다

| ID | 조건 | 심각도 | 제안 연산자 |
|---|---|---|---|
| **C-01** | `stability_rate >= 0.90` 이고 그 단계가 LLM 호출 | P1 | `DOWNGRADE_MODEL` |
| **C-02** | **선택적 보조 단계**(§3-5)가 3회 이상 실행됐는데 `intervention_rate == 0` 이고 토큰을 소비함 | P1 | `MAKE_CONDITIONAL` 또는 `REMOVE` |
| **C-03** | `retry_runs >= 2` 인데 `retry_recovery_rate <= 0.05` | P1 | `REDUCE_LIMIT` |
| **C-04** | LLM 단계인데 출력이 항상 같은 구조이고 `intervention_rate == 0` | P2 | `REPLACE_WITH_CODE` |
| **C-05** | `token_share >= 35%` 인 단계가 다른 단계와 **같은 모델을 공유**함 | P2 | `SPLIT_MODEL` — 그 단계만 떼어내면 모델을 따로 고를 수 있다 |

### 3-2. `QUALITY` — 정확도·안정성을 높인다

| ID | 조건 | 심각도 | 제안 연산자 |
|---|---|---|---|
| **Q-01** | `stability_rate < 0.90` — 같은 입력에 결과가 흔들림 | P1 | `UPGRADE_MODEL` 또는 `ADD_VALIDATION` |
| **Q-02** | `success_rate < 0.95` 이고 `retry_recovery_rate > 0.3` — 재시도가 실제로 살림 | P1 | `INCREASE_LIMIT` |
| **Q-03** | `verifier_enabled == false` 인데 `policy_accuracy < 0.95` | P1 | `ENABLE` |
| **Q-04** | 실패가 특정 `node_role`에 몰림 | P1 | `ADD_VALIDATION` (그 단계에) |
| **Q-05** | `stability_rate >= 0.90` 이고 그 단계의 `provider == "local-deterministic"` | 정보 | `KEEP` — 이미 충분하다 |

> **QUALITY 목표에서는 C-01·C-02를 발화시키지 마라.**
> 검증기가 지금 개입하지 않았다고 해서 불필요한 것이 아니다.
> 안전망은 평소에 조용한 것이 정상이다. 대신 `KEEP`으로 언급하고 넘어간다.

### 3-3. `LATENCY` — 응답 속도를 줄인다

| ID | 조건 | 심각도 | 제안 연산자 |
|---|---|---|---|
| **L-01** | 어떤 단계의 `latency_share >= 35%` | P1 | `DOWNGRADE_MODEL` 또는 `SPLIT_MODEL` |
| **L-02** | `retry_runs`가 전체의 20% 이상 | P1 | `REDUCE_LIMIT` |
| **L-03** | 직렬로 실행되는 LLM 단계가 3개 이상 | P2 | `PARALLELIZE` (가능성만 지적) |
| **L-04** | `intervention_rate == 0` 인 단계가 지연에 기여 | P1 | `MAKE_CONDITIONAL` |

지연 목표에서는 토큰이 아니라 **`latency_share`**로 정렬한다.

### 3-4. `BALANCED` — 명백한 낭비만

C-02 · C-03 · D-04만 검사한다. 즉 **"켜 놓고 일을 안 하는 것"**만 잡는다.
모델 등급이나 품질 강화는 건드리지 않는다. 판단이 갈리는 영역이기 때문이다.

---

### 3-5. 절대 제거를 제안하지 않는 단계 — 모든 목표에서

아래 단계는 **개입률이 0이어도 정상**이다. 안전장치는 평소에 조용한 것이 정상이고,
"한 번도 안 걸렸다"는 것은 "불필요하다"가 아니라 **"지금까지 위험이 없었다"**는 뜻이다.

**C-02의 대상은 아래 세 단계뿐이다. 화이트리스트로 다뤄라.**

| C-02 대상 | 왜 |
|---|---|
| `VERIFY_REASONING` | 결과를 한 번 더 검토하는 **선택적** 단계. 꺼도 업무는 끝난다 |
| `REPAIR_QUERY` | 실패한 쿼리를 고치는 **선택적** 보정 |
| `PLAN` | 계획 수립. 없어도 업무는 진행된다 |

이 셋 밖의 모든 단계는 **개입률이 0이어도 Finding을 만들지 마라.**

| 제외 대상 | 이유 |
|---|---|
| `DECIDE` · `GENERATE_QUERY` · `GENERATE_RESPONSE` | **업무 수행 자체다.** 끄면 에이전트가 일을 못 한다 |
| `VALIDATE_QUERY` | SQL 가드. 끄면 위험한 쿼리가 통과한다 |
| `CHECK_EVIDENCE` | 근거 부족 시 중단시키는 장치 |
| `EXECUTE_TOOL` · `RETRIEVE_SCHEMA` · `CLASSIFY` · `SELECT_POLICY` | 업무 수행 경로 |
| 토큰이 0인 모든 단계 | 이미 비용이 없다. 줄일 것이 없다 |

> `DECIDE`의 개입률이 0이라고 "제거하라"고 하면 안 된다.
> 개입률은 **보조 단계가 값을 하는지** 재는 지표이지,
> 업무 단계가 필요한지 재는 지표가 아니다.

제외 대상은 Finding 대신 보고서 §6 「잘하고 있는 것」에
**"안전장치가 900회 동작했고 위반 0건"** 처럼 긍정적으로 언급해라.

`QUALITY` 목표에서는 C-02 자체가 발화하지 않는다.

## 4. 전체 판정

```
1. SAFETY(D-01)가 있으면            →  BLOCK
2. 아니고 P1 Finding이 있으면        →  ACTION_NEEDED
3. P2·정보만 있으면                  →  MINOR
4. 아무것도 없으면                   →  ALIGNED
```

| 판정 | 뜻 |
|---|---|
| `BLOCK` | 최적화 이전에 안전 문제부터 해결해야 한다 |
| `ACTION_NEEDED` | 목표에 비추어 바꿀 것이 분명히 있다 |
| `MINOR` | 다듬을 것만 있다 |
| `ALIGNED` | **현재 구성이 이미 그 목표에 맞다** |

`ALIGNED`는 "아무것도 못 찾았다"가 아니라 **"목표에 맞게 잘 되어 있다"**는 답이다.
그대로 말해줘라.

## 5. 최적화 연산자

### 줄이는 방향

| 연산자 | 언제 |
|---|---|
| `DOWNGRADE_MODEL` | 결과가 안정적이다. **현재 모델명을 밝히고** 더 낮은 등급 가능성을 제시 (요금 단정 금지) |
| `REPLACE_WITH_CODE` | 출력이 결정론적이다. 코드로 대체 가능 |
| `MAKE_CONDITIONAL` | 항상 켜지 말고 특정 조건에서만 |
| `REMOVE` | 한 번도 일하지 않았다 |
| `REDUCE_LIMIT` | 재시도·반영 상한을 낮춰라 |
| `SPLIT_MODEL` | 이 단계만 다른 모델로 분리 |

### 늘리는 방향

| 연산자 | 언제 |
|---|---|
| `UPGRADE_MODEL` | 결과가 흔들린다. **현재 모델명을 밝히고** 더 강한 등급을 제시 |
| `ENABLE` | 꺼져 있는 검증·보정을 켜라 |
| `INCREASE_LIMIT` | 재시도가 실제로 살려내니 여유를 더 줘라 |
| `ADD_VALIDATION` | 이 단계에 검증을 붙여라 |
| `PARALLELIZE` | 직렬 단계를 병렬로 (가능성만 지적) |

### 유지

| 연산자 | 언제 |
|---|---|
| `KEEP` | 이미 목표에 맞다. 건드리지 마라 |

## 6. 제안 작성 규칙

각 후보는 반드시 이 6가지를 갖는다.

| 항목 | 내용 |
|---|---|
| 무엇을 | 대상 단계(`node_role`) 또는 설정 키 |
| 연산자 | 위 목록 중 하나 |
| 왜 | 근거 Finding ID와 **실제 수치** |
| 목표 적합성 | 이 제안이 **선택된 목표**에 어떻게 기여하는가 |
| 예상 효과 | 토큰 · 호출 수 · 지연 중 **계산 가능한 것만** |
| 확인법 | 적용 후 무엇을 보면 통했는지 아는가 |

지켜야 할 것:

- **근거 수치가 없으면 제안하지 마라.** 일반론("프롬프트를 개선하세요")은 금지다.
- **안전·검증 단계에 `REMOVE`를 제안하지 마라.** §3-5를 먼저 확인한다.
  최대한이 `MAKE_CONDITIONAL`이고, 그때도 위험을 함께 적는다.
- **효과가 큰 순으로** 정렬한다. COST·BALANCED는 `token_share`, LATENCY는 `latency_share`,
  QUALITY는 영향 케이스 수 기준이다.
- 사용자가 밝힌 **제약을 위협하는 제안**은 내지 말거나 위험을 명시한다.
- **`provider == "local-deterministic"`** 인 단계는 모범 사례로 언급하고 건드리지 마라.
  (`model_id`가 아니라 `provider` 필드다)
- 모든 제안에 **"적용 후 재측정 필요"**를 명시한다.
- 절감·개선 추정치를 **지어내지 마라.** 계산할 수 없으면 "추정 불가"라고 써라.
- **금액으로 환산하지 마라.** 요금표가 없다(§0). 토큰 수·호출 수·지연으로만 말한다.

---

## 7. 판정 보류와 신뢰도

- 필요한 필드가 없으면 그 규칙만 **"판정 보류"**로 표시하고 나머지는 진행한다.
  `traces`가 없으면 C-02 · C-04 · D-04 · L-04 · Q-04가 보류된다.
- 케이스가 **3개 미만**이면 모든 Finding을 `참고용`으로 강등한다.
- 반복이 **2회 미만**이면 안정성 기반 규칙(C-01 · C-04 · Q-01 · Q-05)을 `참고용`으로 강등한다.

## 8. 하지 않는 것

- 에이전트의 업무 판단이 옳은지 따지지 않는다 (`agent_output` 내용 해석 금지)
- 코드를 다시 써주지 않는다. **무엇을 어떻게 바꿀지 제안만 한다**
- 실제로 적용하거나 재실행하지 않는다
- 사용자가 밝히지 않은 목표를 추측하지 않는다
