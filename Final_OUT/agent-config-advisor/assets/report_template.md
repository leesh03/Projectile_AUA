# Agent Structure & Cost Diagnosis

| 항목 | 내용 |
|---|---|
| report_id | (자동 생성) |
| 진단 시각 | ISO 시각 |
| 대상 에이전트 | manifest의 provider / model / version |
| 표본 | 테스트케이스 N개 × 반복 M회 = 총 K건 |
| **진단 목표** | **COST / QUALITY / LATENCY / BALANCED** |
| 지켜야 할 제약 | 사용자가 밝힌 선 (없으면 "없음") |
| **판정** | **ALIGNED / MINOR / ACTION_NEEDED / BLOCK** |

> 이 진단은 위 목표를 기준으로 했습니다.
> 목표가 다르면 결론도 달라집니다.

## 0. 입력 점검

| 항목 | 결과 |
|---|---|
| 사용한 기록 | N건 |
| 제외한 기록 | N건 — 사유 |
| 판정 보류된 규칙 | 규칙 ID — 없는 필드 |

## 5. 제안

효과가 큰 순으로 정렬. (COST·BALANCED는 토큰 비중, LATENCY는 지연 비중,
QUALITY는 영향 케이스 수 기준)

### 제안 1

| 항목 | 내용 |
|---|---|
| 무엇을 | 대상 단계 / 설정 키 |
| 연산자 | 줄이기: DOWNGRADE_MODEL / REPLACE_WITH_CODE / MAKE_CONDITIONAL / REMOVE / REDUCE_LIMIT / SPLIT_MODEL<br>늘리기: UPGRADE_MODEL / ENABLE / INCREASE_LIMIT / ADD_VALIDATION / PARALLELIZE<br>유지: KEEP |
| 왜 | 근거 Finding ID + 실제 수치 |
| 목표 적합성 | 이 제안이 선택된 목표에 어떻게 기여하는가 |
| 예상 효과 | 토큰 __% · 호출 __회/케이스 · 지연 __ms (계산 불가면 "추정 불가") |
| 제약 영향 | 사용자가 밝힌 제약을 위협하는가 |
| 확인법 | 적용 후 볼 지표와 목표값 |

> 이 제안들은 검증되지 않았습니다. 적용 후 재측정이 필요합니다.

## 6. 잘하고 있는 것

이미 최적화된 부분을 짚는다. 예: 이미 코드로 처리되는 단계.

## 7. 다른 목표였다면

선택한 목표가 아닌 다른 목표로 봤을 때 결론이 크게 달라지는 지점을
한두 줄로 짚는다. 예: "품질 우선이었다면 VERIFY_REASONING은 유지 권고였을 것."

사용자가 목표를 잘못 골랐을 수도 있으므로 되돌아볼 여지를 남긴다.

## 8. 이 진단이 말하지 못하는 것

- 표본 크기와 반복 횟수의 한계
- 판정 보류된 규칙과 그 이유
- 업무 정확성 자체는 판단하지 않음
- 제안은 검증되지 않았음. 적용 후 재측정 필요
